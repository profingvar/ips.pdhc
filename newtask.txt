#928 last_updated — DONE AND DEPLOYED (2026-11-04). Ticket closed.
------------------------------------------------------------------
1242 tests pass (was 1231). No migration: `onupdate` is ORM-level.

`last_updated` had `default=utcnow` and no `onupdate`, so it was a CREATION
timestamp wearing a modification timestamp's name — while carrying an index
that invites the "what changed recently" query it could not answer. Two live
queries take that invitation (`fhir_service.search_resources:137`,
`admin.patient_detail:359`) and returned creation order; they now return
modification order, which is a deliberate behaviour change with a test.

THE MEASUREMENT THE TICKET DID NOT HAVE: 2355 of 4780 rows had
`last_updated != created_at`, every difference under 1 ms, and every one with
`last_updated` EARLIER. A modification can only be LATER, so that was proof of
two independent clock reads in one INSERT. A `before_insert` listener now
shares one read, so a difference finally MEANS a modification.

version_id is deliberately NOT bumped in place. `update_resource` is
append-only (new row at version+1, old one `superseded`) and measured 4780
rows / all active / 0 superseded — the path has NEVER run. A row claiming v2
with no v1 would assert a history that does not exist. #934 carries the real
question: should a backfill create a version?

Nothing serves `meta.lastUpdated` from this column (all 11 `meta` builders do
`tag`/`profile` only), so this is an internal fix and not a conformance one —
which is the gating question #928 asked.

DEPLOYED AND VERIFIED by a write that was ROLLED BACK: insert gives identical
timestamps to the microsecond, an update moves `last_updated` and not
`created_at`, `version_id` stays 1, and the row count is 4780 before and after.
Structural checks in the container confirm `onupdate` is on `last_updated` and
NOT on `created_at`. /api/v1/health 200, smoke 10/10.

The 2355 pre-existing rows with `last_updated` EARLIER are untouched: history is
not repaired, by design.

#927 REMAINS OPEN, and #928 corrects part of its reasoning: it used
`last_updated` unchanged as evidence, and with no `onupdate` that column could
never have moved — so it eliminated nothing. A lead was chased and killed: both
#927 resource ids are UUIDv5 (deterministic, `implant_routes._derived_ids`), so

NEXT PHASE: THIS SERVICE BECOMES eps.pdhc
------------------------------------------
Operator decision, 2026-11-04, following the EPS work (#876 epic, #905).

Measured scope: 845 occurrences across 16 top-level directories. Only 189 of
them are in THIS repo - the cost is in the eight sibling services that carry
IPS_BASE_URL and IPS_API_KEY in their own .env files and clients, plus the
website.

READ progress.md's "NEXT PHASE" section before touching anything. It carries
the measurement, the six decisions that come before any rename, and the
precedent: the gateway -> planp rename of March 2026 changed the Docker
volume namespace and a cp in the wrong direction destroyed a production
database irrecoverably. Plan's database is still called `pdhc_gateway` eight
months later.

The short version of the decisions:
  1. Does the data move at all? (ips_pgdata, ips-db-1, ips_db, ips_user.)
     Keeping them is ugly and safe. Plan proves ugly-and-safe survives years.
  2. New eps.pdhc.se vhost + TLS cert, with ips.pdhc.se kept answering until
     every caller has moved. Both live at once, or callers break one by one.
  3. sso.pdhc needs an _EPS client pair registered FIRST, by the operator -
     sso is outside Claude's envelope (CLAUDE.md §15).
  4. Eight .env files accept BOTH names, repoint one service per run, each
     verified by its own deploy/smoke_siblings.py before and after, then
     remove the old name.
  5. CLAUDE.md §3 and the website's service list.
  6. Leave #-numbers in comments alone. They record when a decision was
     taken (CLAUDE.md §2).

Do NOT start with a sed. The #816 split showed a blind replace breaks correct
references that merely share a string, and CLAUDE.md's KNOWN_SERVICES table
was wrong twice because a hand survey globbed a filename instead of searching
for the symbol.
