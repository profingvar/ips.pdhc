Design principle: All internal references use GUIDs (UUID v4). FHIR resource IDs are separate identifiers used for FHIR API compatibility. FHIR resources are stored as JSONB to preserve semantic structure and allow incremental profile support.

FHIR R5 Compliance

Supported Resource Types

Patient, Condition, Observation, MedicationStatement, AllergyIntolerance, Immunization, Procedure, DocumentReference, DiagnosticReport

IPS Profile

  • Profile URL: http://hl7.org/fhir/uv/ips/StructureDefinition/Bundle-uv-ips
  • Bundle type: document
  • Composition uses LOINC section codes
  • Empty sections include emptyReason coding
  • $ips operation supports full and minimal modes

Error Handling

FHIR endpoints return OperationOutcome for all errors (4xx/5xx) per the FHIR specification.

IPS Generation

The IPS generation service (app/services/ips_generator.py) performs a deterministic transformation:

  1. Identify the patient and composition date
  2. Collect clinical resources by type for that patient
  3. Build a FHIR Composition with LOINC-coded sections
  4. Assemble into a document Bundle with resource references

Security Model

Four concentric controls: authentication, authorization, data minimization, and auditability.

AUTH_DISABLEDSynthetic dev user attachedLocal development only

Public Endpoints (no auth required)

/api/v1/health, /api/v1/metrics, /fhir/metadata

Audit Trail

All significant operations are logged with: actor identity, patient context (when applicable), event type, request method/path, IP address, and timestamp. Sensitive reads (e.g. snapshot bundle retrieval) are specifically flagged.

Production requirements: Set AUTH_DISABLED=false. Enforce HTTPS via nginx. Never log tokens, keys, or raw patient identifiers. Audit logs need retention policies and restricted access.
