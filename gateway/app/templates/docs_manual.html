Service Overview

The IPS Server produces and serves International Patient Summaries (IPS) using the FHIR R5 standard. It provides:

  • A FHIR REST API (/fhir/...) for standards-based interoperability
  • An Application API (/api/v1/...) for operational workflows
  • An Admin UI (/admin/...) for operators

Admin UI

The Admin UI is accessible at /admin/. It requires no separate authentication when accessed through the same host. The navigation bar provides links to all pages.

Dashboard

The dashboard (/admin/) displays:

  • Service Status — database connectivity indicator
  • Resource Counts — patients, FHIR resources, IPS cards, snapshots, push jobs, audit events
  • Recent Audit Events — the last 20 events with timestamp, type, actor, method, and path

Patient Browser

The patient browser (/admin/patients) allows operators to search and inspect patients.

Searching

Use the search box to find patients by family name, given name, or identifier value. The search is case-insensitive and partial-match.

Patient Detail

Click "View" on any patient to see their detail page showing:

  • Demographics — GUID, identifier, birth date, gender, status, creation date
  • Summary — counts of FHIR resources, IPS cards, and snapshots
  • FHIR Resources — table of all clinical resources (type, ID, version, status, last updated)
  • IPS Cards — table of cards with title, mode, status, and snapshot count
  • Snapshots — table of all snapshots with composition date and resource count

Push Monitor

The push monitor (/admin/push) provides visibility into the IPS distribution system.

Destinations

The destinations table shows all configured push targets with name, type, endpoint URL, auth method, active/inactive status, and job count.

Push Jobs

The jobs table shows all push jobs with their status, attempt count, response code, and error message. Use the status filter dropdown to view only jobs in a specific state.

Queue Statistics

Four cards show the count of jobs by status: Queued, In Progress, Completed, Failed.

IPS Workflow

The standard workflow for producing and distributing an IPS:

Step 1 — Ingest patient and clinical data

Create a Patient via POST /fhir/Patient, then add clinical resources (Condition, Observation, MedicationStatement, etc.) via POST /fhir/{ResourceType}. Each clinical resource must reference the patient via subject.reference or patient.reference.

Step 2 — Generate IPS on demand (optional)

Call GET /fhir/Patient/{id}/$ips to generate an IPS bundle in real time. Use ?mode=minimal for a reduced set (conditions, medications, allergies only).

Step 3 — Create an IPS card

Call POST /api/v1/ips/cards with the patient GUID to create a named summary handle. Set mode to full or minimal.

Step 4 — Take a snapshot

Call POST /api/v1/ips/cards/{card_guid}/snapshots to generate and store an immutable point-in-time bundle. The snapshot captures exactly what the IPS contains at that moment.

Step 5 — Distribute (push)

Create a push destination (POST /api/v1/push/destinations) and then create a push job (POST /api/v1/push/jobs) with the snapshot GUID and destination GUID. Monitor delivery via the Push Monitor page or GET /api/v1/push/jobs.

API Key Management

API keys provide machine-to-machine authentication for integrations.

Creating a key

POST /api/v1/auth/keys with an optional label and scopes. The response includes the plaintext key exactly once — store it securely. It will never be shown again.

Listing keys

GET /api/v1/auth/keys shows key metadata (prefix, label, creation date, last used) but never the hash or plaintext.

Revoking a key

DELETE /api/v1/auth/keys/{guid} revokes the key immediately. This is irreversible.

Rotating a key

POST /api/v1/auth/keys/{guid}/rotate revokes the old key and issues a new one in a single operation. The new plaintext is returned once.

Security: Review active keys monthly. Revoke unused keys (no activity in 30+ days). Rotate all service-account keys at least every 90 days. After a security incident: revoke all keys and issue new ones.

Maintenance Procedures

Health monitoring

Poll GET /api/v1/health periodically. Status "ok" means all systems operational. Status "degraded" means the database is unreachable.

Database backup

The PostgreSQL database runs in Docker. Back up via:

docker-compose exec db pg_dump -U ips_user ips_db > backup_$(date +%Y%m%d).sql

Restarting the service

cd /usr/local/www/ips.pdhc/gateway
docker-compose down
docker-compose up -d
Note: Use docker-compose up -d --force-recreate after editing .env — a plain restart does not re-read environment variables.

Viewing logs

docker-compose logs -f app     # Application logs
docker-compose logs -f db      # Database logs
